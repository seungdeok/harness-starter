# 절차를 바꾸는 변경은 절차 단위로 설계하고 절차 단위로 검증한다

- 날짜: 2026-08-02
- 작업/PR: [#36](https://github.com/seungdeok/harness-starter/pull/36) (이슈 [#34](https://github.com/seungdeok/harness-starter/issues/34)), 브랜치 `ISSUE-34`

## 문제

`/harness:setup` 재실행 시 "무엇이 그대로 남고 무엇이 바뀌는지"를 알 수 없다는 이슈를 고쳤다.
해법은 **사전 스캔 절을 추가**하는 것이었고, 계획·구현·검증이 전부 그 새 절에만 초점을 맞췄다.

같은 사이클에서 **같은 모양의 실수가 두 번** 나왔다. 하나는 리뷰가, 하나는 검증이 잡았다.

| 단계 | 놓친 것 | 잡은 것 |
| --- | --- | --- |
| 설계 | 새 확인 지점만 설계하고 **기존 확인 지점 4곳**을 안 봤다 | `/plan-eng-review` |
| 검증 | 새 절차의 **부품**만 검증하고 절차 전체를 안 돌렸다 | V9·V10 (임시 레포 2회 실행) |

## 원인 1 — "추가"를 설계하면서 "기존"을 안 셌다

계획은 이렇게 적혀 있었다.

> **`다름` 이 1개 이상이면 AskUserQuestion 을 한 번만** 띄워 …
> AC9: `CLAUDE.md` 마커 처리 문장(현 :115-118)이 **문자열 그대로** 남아 있다.

두 문장이 같은 계획서에 있었다. 그런데 `SKILL.md` 에는 확인 지점이 이미 넷 있었다.

```
:52   이미 HARNESS_* 값이 있으면 현재 값을 보여주고 갱신 여부를 확인해요.
:97   두 SHA 를 보여주고 갱신할지 물어봐요.
:116  append 전에 추가될 내용을 사용자에게 보여주고 확인받아요.
:117  마커가 있으면 append 하지 않고, 마커 사이 내용을 갱신할지 물어봐요.
```

계획은 이 넷을 **한 번도 언급하지 않았다.** 그대로 두면 사용자는 스캔에서 "전부 갱신"을 고른 뒤
:52·:97·:117 에서 같은 걸 세 번 더 확인받는다 — **확인이 4곳 → 5곳으로 늘어난다.**
"확인을 한 번에"라는 이슈의 목적이 정확히 반대로 뒤집힌다.

핵심은 계획이 **틀린 말을 안 했다는 것**이다. 새 절에 대한 서술은 전부 옳았다. 빠진 건
"그래서 기존 것은 어떻게 되는가"라는 질문 자체였고, 그건 새 절만 들여다봐서는 절대 안 나온다.

## 원인 2 — 부품은 전부 돌았는데 절차는 한 번도 안 돌았다

검증 계획 V1~V8 은 이랬다.

| V | 내용 |
| --- | --- |
| V1·V2 | `grep -qxF` 가 있음/없음 두 상태에서 옳은 exit code 를 내는가 |
| V3 | `.gitignore` 부재 시 에러가 안 나는가 |
| V4·V5 | `test -f` / 마커 `grep` |
| V6 | 낡은 `§N` 참조가 남았는가 |
| V7 | `pipeline.py selftest` |
| V8 | 절 순서가 1→2→3→4→5→6 인가 |

**8건 전부 통과했다.** 그리고 이 중 어느 것도 setup 을 실행하지 않는다. `selftest` 는 `SKILL.md` 를
읽지도 않고(이 레포의 CI 는 `.claude-plugin/*.json` 만 본다 — [ci-check-coverage.md](ci-check-coverage.md)),
나머지는 스캔이 *쓸* 셸 명령이 도는지만 본다.

그래서 임시 git 레포에 새 절차를 그대로 적용해 setup 을 2회 돌렸더니(V9·V10) 이게 나왔다.

```
| CLAUDE.md 마커 블록 | 다름 |     ← 재실행마다 영구히
[확인 프롬프트] 다름=1건 → 1회 띄움
[§6 종료 안내] (빈칸 — "모두 최신이에요" 가 영영 안 나옴)
```

스캔 표가 `마커 존재` → `다름` 으로 매핑하는데, **최초 실행이 그 마커를 넣는다.** 그러니 그 뒤
모든 재실행에서 `다름 ≥ 1` 이고, 결과적으로 수용 기준 두 개가 **도달 불가능한 죽은 조건**이었다.

- AC4 "다름 0개면 확인 프롬프트를 띄우지 않아요" → 도달 불가
- AC8 "변경 0건에도 '모두 최신' 출력" → 도달 불가

더 나쁜 건 §1 의 **기본 선택지**(프로젝트 CLAUDE.md 에 append)를 고른 사용자만 이 경로에 걸린다는
것이다. CLAUDE.md 를 `건너뛰기` 한 사용자는 정상 동작한다.

### 기존 규칙이 이걸 못 잡는 이유

GUARDRAILS 에 이미 *"정방향 통과를 근거로 삼기 전에 그 실행이 대상 코드 경로를 실제로 밟는지
역방향으로 확인한다"* 가 있다(근거: [verification-trigger-coverage.md](verification-trigger-coverage.md)).
그 규칙은 **지켰다** — V11 로 `phases/` 를 주입해 `없음`→`다름` 이 뒤집히는 걸 확인했다.

그런데도 안 잡혔다. 그 규칙이 다루는 실패는 **"아무것도 안 돌았다"** 이고, 이번 실패는
**"여러 개가 돌았는데 전부 부품이었다"** 이기 때문이다. 부품은 각각 진짜로 돌고 역방향도 통과한다.
절차가 한 번도 안 돌았을 뿐이다.

산문 스킬에서 이 미끄러짐이 특히 쉬운 이유는, "대상 코드 경로"가 **코드가 아니라 절차**라서
검증 대상을 잡을 때 자연스럽게 실행 가능한 부품(`grep`·`test`·`selftest`)으로 손이 가기 때문이다.

## 해결

**설계 쪽** — 리뷰가 기존 확인 지점을 전수 조사하게 했고(`grep -n '물어봐요\|확인해요\|확인받아요'`),
넷 중 셋을 "스캔 결정을 적용한다"로 바꿨다. 하나(`:116`)는 신규 생성 경로라 그대로 뒀다.
ADR-008 이 요구한 "로컬 수정이 있습니다" 경고도 **함께 옮겼다** — 묻는 자리를 옮기면서 경고를
빠뜨리면 원래 버그보다 나쁘다.

**검증 쪽** — 임시 git 레포를 만들어 새 절차를 그대로 적용하고, **두 상태**로 돌렸다.

```
V9  최초 실행   → 전 항목 `없음`, 확인 0회, 생성 요약 출력
V10 곧바로 재실행 → 전 항목 `동일`, "나머지 모두 최신" 출력
V11 역방향     → `phases/` 주입 시 `없음`→`다름`, 원복 시 복귀
```

V10 이 FAIL 을 냈고, 그게 죽은 조건의 유일한 발견 경로였다. V11 은 별개로 필요하다 —
"스캔이 실제 파일 상태를 읽는가"는 V9·V10 이 답하지 않는다(둘 다 정방향이다).

## 재발 방지

- **확인·게이트 절차를 새로 추가할 때는 기존 확인 지점을 전수 조사해 어떻게 할지 함께 정한다.**
  "추가"만 설계하면 확인 횟수가 늘어 원래 목적이 뒤집힌다. 계획서에 새 절의 서술이 아무리
  정확해도, 기존 지점을 한 줄도 언급하지 않았다면 그건 설계가 덜 된 것이다.
  값싼 확인법: 대상 파일에서 "묻는다/확인한다" 류를 grep 해 개수를 세고, 변경 후 개수를 다시 센다.
- **절차(산문 스킬·런북)를 바꿨으면 부품이 아니라 절차 전체를 두 상태로 돌려본다.**
  최초 실행과 재실행은 다른 코드 경로다 — 재실행에서만 도달하는 조건이 있고, 그게 죽어 있는지는
  돌려보기 전엔 알 수 없다. 부품 검증이 전부 초록불인 것은 아무 보증이 아니다.
- 이 규칙은 [verification-trigger-coverage.md](verification-trigger-coverage.md) 의
  **다음 단계**다. 그건 "그 실행이 대상 경로를 밟는가"를 묻고, 이건 "밟은 것이 부품인가 절차인가"를
  묻는다. 둘 다 통과해야 한다.

→ GUARDRAILS.md 에 두 줄 승격.

## 부수 확인 — 남는 미검증을 정확히 적는다

probe 는 **문서에 적힌 절차를 사람이 그대로 적용한 것**이다. "절차가 실행 가능하고 요구된 출력을
낸다"까지가 보증 범위이고, "실제 에이전트가 이 산문을 읽고 같은 판정을 내리는가"는 검증하지 않았다.
산문 스킬의 구조적 한계이고 CI 로도 못 잡는다(ADR-010 이 이 커버리지 공백을 이미 인정한 비용으로
기록해 뒀다).

이걸 PR 본문에 명시적으로 적었다 — 보증하지 못하는 것을 적어두지 않으면 다음 사람이 통과를
보증으로 읽는다([gate-ref-symmetry.md](gate-ref-symmetry.md) 의 "판정할 수 없는 것을 게이트로
만들려 하지 말고, 판정할 수 없다는 사실을 정확히 출력한다"와 같은 축).
